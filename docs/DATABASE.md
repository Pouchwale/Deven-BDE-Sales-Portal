# The database: plain SQL, one source, two dialects

You asked for the SQL to be maintained so that moving to production is easy.
This is how that works.

## The rule

**`backend/app/db/sql/*.sql` is the source of truth for the schema.**

The SQLAlchemy models in `backend/app/models/` mirror it. They never create
tables. If the two disagree, `tests/test_schema_parity.py` fails the build —
so a column added in Python and forgotten in SQL is caught at test time, not
by a 500 in production.

There is no Alembic. Alembic's autogenerate would make the Python models the
source of truth and reduce the SQL to a build artefact, which is the opposite
of what you asked for. What that costs us is autogenerate and automatic
downgrades; what it buys is that the statements in the repo are exactly the
statements that will run against production, reviewable by a DBA before they
do.

## One file, both dialects

Dev runs SQLite, production runs PostgreSQL. Rather than maintaining two DDL
files that drift apart, the SQL carries typed placeholders which
`app/db/render.py` substitutes:

| Placeholder | SQLite | PostgreSQL |
|---|---|---|
| `{{UUID}}` | `CHAR(36)` | `uuid` |
| `{{JSON}}` | `TEXT` | `jsonb` |
| `{{TS}}` | `TIMESTAMP` | `timestamptz` |
| `{{BOOL}}` | `BOOLEAN` | `boolean` |
| `{{NOW}}` | `CURRENT_TIMESTAMP` | `now()` |

An unrecognised placeholder raises rather than reaching the database as
literal text, where it would produce a baffling syntax error.

Everything else in the schema is written in SQL both accept, including the
two partial unique indexes and the recursive CTE the visibility model uses.

## Commands

```bash
cd backend

python -m app.db.migrate status                 # what is applied, what is pending
python -m app.db.migrate upgrade                # apply pending migrations
python -m app.db.migrate render --dialect postgresql --out ../docs/schema.postgres.sql
python -m app.db.migrate reset                  # DEV ONLY: drop the SQLite file and re-apply
```

`docs/schema.postgres.sql` is the rendered production DDL, regenerated by that
`render` command. It is the file to hand to a DBA or diff against a live
database. Do not edit it — edit the migration and re-render.

## Changing the schema

1. Add a new numbered file: `backend/app/db/sql/0002_<what_it_does>.sql`.
2. Write plain SQL, using the placeholders for the five portable types.
3. `python -m app.db.migrate upgrade`.
4. Update the matching model in `backend/app/models/`.
5. `pytest` — the parity test tells you if you missed something.
6. Re-render `docs/schema.postgres.sql`.

`0002_timelines_and_undo.sql` is a worked example of the whole flow: it was
added after `0001` had already been applied and shipped data, and
`migrate upgrade` applied it incrementally — customer timelines, undo columns
and the feedback-to-customer link, with the 17 real SAP customers untouched.

**Applied migrations are immutable.** The runner stores a SHA-256 of each
file and refuses to run if an already-applied file has changed, because the
database has already executed the old text:

```
RuntimeError: Migration 0001_initial.sql has changed since it was applied.
Applied migrations are immutable - the database has already run the old text.
Add a new numbered .sql file with the change instead of editing this one.
```

Before release, when nothing has shipped, `python -m app.db.migrate reset`
is the honest way out. After release, add a new file.

## Going to production

1. Provision PostgreSQL and set `DATABASE_URL=postgresql+psycopg2://...`.
2. `pip install psycopg2-binary` (excluded from Windows dev installs).
3. `python -m app.db.migrate upgrade` — the same files, rendered for Postgres.
4. `python -m app.seeds.seed` — idempotent; safe to run against a live database.
5. Run the test suite against Postgres before calling it done:
   ```bash
   TEST_DATABASE_URL=postgresql+psycopg2://user:pass@host/bde_test pytest
   ```
   The suite builds its schema by running the real migrations, so this proves
   the migrations work on Postgres rather than assuming it.

## Two things worth knowing about SQLite

Both are handled in `app/db/session.py`, and both are silent data-integrity
bugs if you forget them on a new project:

* SQLite ships with **foreign keys disabled**. Without `PRAGMA foreign_keys=ON`,
  every `REFERENCES` clause in the schema is decoration.
* pysqlite's legacy transaction handling opens and commits transactions on its
  own schedule, which breaks `SAVEPOINT` and makes rollback unreliable. The
  driver's `isolation_level` is set to `None` and SQLAlchemy emits `BEGIN`
  itself. Without this pair, the guarantee that an audit row lands in the same
  transaction as the change it describes is not actually kept.

## Timestamps

Stored as **naive UTC** in every dialect, because SQLite has no `timestamptz`.
The PostgreSQL connection is pinned to UTC so a naive value is never
reinterpreted in the server's local zone. `Asia/Kolkata` is a presentation
concern, applied in the frontend.

Use `app.db.base.utcnow()`. Never call `datetime.now()` without a timezone.
